# RuleTrip v0.3.0 — Attributed, Repeatable Trips

RuleTrip v0.3.0 strengthens the inference behind `ALIVE`. A non-zero exit can no longer impersonate attributed detection when a differential literal sensor is configured, and repeated experiments must agree unanimously.

## Highlights

- differential literal sensors over bounded stdout, stderr, or combined output—absent on clean controls, present on mutations;
- one to five clean-control and mutation confirmations in fresh worktrees;
- missing, pre-existing, or baseline-obscured sensors and mixed exits classified as **INCONCLUSIVE**;
- confirmation and attribution facts in Markdown, JSON, and SARIF, with JUnit retaining the conservative outcome projection;
- top-level attribution coverage plus matching GitHub Action outputs;
- hostile tests covering unrelated failures and flaky outcomes;
- Action-as-an-Action CI across Ubuntu, macOS, and Windows;
- continued zero-runtime-dependency design.

## Upgrade

```bash
npm install --save-dev github:Dean00dev/RuleTrip#v0.3.0
```

Configuration schema version 1 remains valid. Existing configurations keep their one-run, exit-only behaviour. Newly generated configurations request two confirmation runs and add sensors only where the shipped preset has a stable literal signal.

## Assurance boundary

A differential literal strengthens attribution but is not causal proof: an unrelated mutation-only failure could emit the same text, and a guard controls its own output. Repetition exposes observed instability but does not establish a future reliability rate. RuleTrip still measures a bounded process response; it does not certify a repository.
